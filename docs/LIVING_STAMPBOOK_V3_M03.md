# POINT+ Living Stampbook V3 — M03 Release Notes

## Milestone
**M03 — Image & Stamp Interaction** on the existing `feat/living-stampbook-v3` branch and the SAME Draft PR #28. M04 Flexible Redemption and M05 autosave/animation are not implemented in M03.

### Private photo scrapbook
- An additive schema change permits `image` elements in `living_book_elements` while retaining text and drawing validation from M02.
- A new private Supabase Storage bucket, `pointplus-living-photos`, restricts MIME to PNG, JPEG, WebP and server upload size to 6 MiB. **No public URLs.**
- Keys have fixed `space_uuid/book_uuid/page_uuid/element_uuid.ext` format. RLS restricts reading to authenticated room members, and insertion/removal to the active book owner. Photo RPCs also enforce page/book/owner identity.
- Browser optimizes oversized photographs to a WebP thumbnail at up to 2048 pixels on the long edge (when browser supports ImageBitmap and canvas). Server validates MIME, actual binary headers, dimensions 1–8192 pixels, static formats and maximum bytes before upload; it rejects SVG, animated WebP and APNG.
- Browser receives expiring 20-minute signed URLs generated by authenticated server Supabase client, never storage paths from arbitrary external image URLs. Images are loaded page-by-page; geometric styling and crop rectangles persist with versions.
- Uploaded photos are **decoration only**, not spendable stamps. Photo metadata is validated again by PostgreSQL. A deleted photo is soft-deleted in the page ledger and the owner session attempts to remove its Storage object. If removal fails, the editor reports an orphan-file cleanup issue; a later cleanup/maintenance process should reconcile these.

### Real stamps
Authoritative records are in NEW tables:
- `living_stamp_requests`: book/page/recipient/giver, authorized asset, note, full normalized placement, approval state, unique idempotency key.
- `living_stamp_marks`: permanent stamp UUID, original request/giver/recipient identity, page/placement/rotation/scale, current `available` or `peeled` state, optimistic version and peel metadata.
- `living_stamp_events`: append-only grant/transform/peel events with actors and timestamps. Direct clients cannot modify this ledger.

Authorized RPCs:
- `pointplus_give_living_stamp`: caller must be a member and listed in `living_book_givers`; book must be active; page and artwork valid; book row lock serializes concurrent grants; retries with same idempotency key reuse the original request (never mint twice).
- `pointplus_review_living_stamp`: when the approval policy requires review, only an independent recipient/member reviewer may approve/reject; no self-approval. Approved requests mint exactly one permanent mark, rejected requests mint none.
- `pointplus_cancel_living_stamp_request`: authorized giver/owner can cancel pending requests without issuing marks.
- `pointplus_transform_living_stamp`: active owner-only move within or across book pages, resize 0.3–3×, rotation -180…180°, requiring current version; no new stamp IDs.
- `pointplus_peel_living_stamp`: active owner-only action on an available stamp with matching version; changes state to `peeled`, appends event, leaves faded paper trace and does **not** restore spendable balance.
- No reward/redemption implementation is present until M04.

### UI
- Giver chooses a "ประทับแสตมป์" tool then taps/clicks paper coordinates and picks artwork, note, free rotation and size.
- Direct stamp appears on paper after verified server receipt; pending stamp has transparent "รออนุมัติ" preview without counting as received.
- Independent reviewer can approve/reject, giver can cancel a pending request.
- Owner can drag available stamps, choose a different page, alter position/rotation/size and explicitly confirm peeling. Peeled stamp stays visible as a ghost trace.
- Owner can upload photographs and resize/rotate/crop them through existing editor object properties; users without edit permission see a read-only book.
- Stamp Card fixed-slot flow and all earlier M01/M02 page/text/drawing features are unchanged.
